# 重寫流程與對等驗證

適用於：重寫現有收錄的工具，以及往後新增的任何工具。

## 0. 參考原作程式改寫（2026-10-01 起）

所有工具都可以（也應該）閱讀原作的程式——`tools/<id>/` 的舊檔、`vendor/`、上游原作；已上線、舊檔已刪的工具用
ATTRIBUTION「本站重寫的工具」表的 commit 取回——理解功能、演算法與數值後，改寫成 `web/` 的共用元件與模組：
用本專案的結構、元件、設計 token 與用詞，不整段貼上、不逐行轉寫舊的檔案。

| 原作授權（PLAN.md 第 2 節） | 素材與文字 | 授權聲明 |
|---|---|---|
| **MIT、CC0 等開放授權** | 範本、預設集、範例可以沿用（翻成繁中） | 原作的授權全文放 `web/src/tools/<id>/UPSTREAM_LICENSE`，建置時併入 `assets/build/THIRD_PARTY_NOTICES.md` |
| **未授權、作者條款限制** | 圖片素材、範本文字、範例資料不沿用，自己做 | — |

角色因此簡化：**實作者**讀原作程式與規格後改寫（規格還沒有功能清單時先寫第 1 節）；**驗證者**照第 4 節做對等驗證；
**主控**審查、裁定、合併、上線，小幅修正可以自己做。下面第 1 節「無塵室」的角色分工是 2026-10-01 以前的做法，
已寫好的規格與對等驗證紀錄照常沿用。

## 1. 角色（2026-10-01 以前的無塵室做法，僅供參考）

| 角色 | 可以看 | 不可以看 | 產出 |
|---|---|---|---|
| **觀察者** | 舊版工具（`tools/<id>/`、`vendor/`）、上游原作、實際操作與匯出結果 | — | `docs/refactor/specs/<id>.md`（行為規格） |
| **審查者**（主控） | 全部 | — | 確認規格沒有夾帶程式表達後放行 |
| **實作者** | 規格、`docs/refactor/` 其他文件、`web/` 框架與元件、npm 套件文件 | 舊版工具的程式碼與標記（`tools/<id>/` 舊檔、`vendor/`、上游原作、scratchpad 裡的上游 clone） | `web/src/tools/<id>/` |
| **驗證者** | 全部（可以操作舊版與新版） | — | 規格裡的「對等驗證紀錄」 |

觀察者與實作者必須是不同的子代理。驗證者可以是觀察者本人或主控。

## 2. 行為規格（specs/<id>.md）怎麼寫

**只寫看得到的結果**，不寫實作。禁止出現：程式碼、虛擬碼、正規表示式、CSS、HTML 片段；原作的變數名、函式名、
資料結構、內部常數、亂數種子算式；原作的範本名稱、範例文字、介面文案、說明文字、圖示描述、版面配置。

範本：

```markdown
# <工具名>（<id>）行為規格

## 0. 概要
一段話說明用途、輸入、輸出。靈感來源：<名稱>（<連結>）。

## 1. 功能清單（對等驗證以此為準）
| 編號 | 功能 | 行為描述（看得到的結果） | 預設值／範圍 | 驗證方式 |
|---|---|---|---|---|
| F01 | … | … | … | 自動（腳本）／目視（截圖並排）／資料比對 |

## 2. 輸入
檔案格式、可接受的範圍、錯誤時的反應。

## 3. 輸出
檔案格式與內容規則（例如 ZIP 內的結構、JSON 欄位的意義、圖片尺寸、檔名規則的概念）。
**外部資料格式（CCFOLIA 的 JSON、ZIP 結構、OBS 的 DOM 選擇器）屬於事實規格，可以完整寫出欄位與結構。**

## 4. 互動與手感
動畫時長、緩動曲線取樣、快捷鍵、存檔與還原行為、預設值。

## 5. 容易做壞的地方

## 6. 對等驗證紀錄（驗證者填）
| 編號 | 結果 | 方法與證據（截圖／腳本路徑） | 備註 |
```

說明：
- 功能清單要**完整**：舊版介面上每一個控制項、每一種輸出、每一個快捷鍵都要對應到一個編號。
- 外部資料格式（CCFOLIA、OBS、Discord Streamkit 的 DOM 等）是公開的事實，不是原作的表達，可以完整描述；
  但原作自己的存檔格式不必照抄（新版自己設計，必要時提供舊存檔的匯入）。
- 量測值寫成觀察到的數字（例如「起點在下方約 0.55 倍字高」），標示「約」或「粗估」。

## 3. 實作守則

- 只用 `web/src/ui` 的元件與 `web/src/core`、`web/src/ccfolia` 的模組；缺的先做成共用元件（放對位置、寫進 DESIGN.md），
  工具專屬的才放在工具目錄。
- 範本、範例文字、預設集、圖片素材全部自己做（繁中）。
- 介面文字放在 `web/src/tools/<id>/strings.ts`，用詞照 DESIGN.md 的用詞表。
- 頁尾只放「靈感來源：<名稱>」連結，不放原作者的其他標示。

## 4. 對等驗證

上線前，規格裡**每一個功能編號**都要有驗證結果：

| 類型 | 方法 |
|---|---|
| 資料輸出（ZIP、JSON、CSS、文字） | 同樣的輸入分別餵給舊版與新版，解析輸出後比對結構與值；允許的差異（例如欄位順序、時間戳）要事先列明 |
| 圖片／動畫輸出 | 同樣設定下抽固定時間點的影格並排，必要時算像素差；字型等刻意的差異要寫明 |
| 互動 | Playwright 腳本操作兩邊，比對狀態與結果；或並排截圖目視 |
| 效能 | 大檔案、長動畫的匯出時間與記憶體不得明顯變差 |

結果寫回規格的「對等驗證紀錄」。有任何「未通過」就不能上線；刻意的差異（例如改善了原作的錯誤、拿掉了失效的功能）
要寫明理由並由主控確認。

## 5. 上線清單

1. 規格的功能清單全部驗證通過（或差異已確認）。
2. `web/` 的單元測試與該工具的 Playwright 測試通過；視覺回歸基準圖已更新。
3. 記下舊版所在的 `main` commit（刪除前最後一個含舊版的 commit；寫進 ATTRIBUTION 的「本站重寫的工具」表）。
   本環境的 git 代理只允許推送工作分支，無法推送標籤，所以用 `main` 上的 commit 代替 `legacy/<id>` 標籤。
4. `web/src/registry.ts` 把該工具改成「已上線」，建置後產物寫到 `tools/<id>/`；刪除舊版檔案、字典、`vendor/` 原始碼、
   舊的 smoke 測試段落。
5. 首頁卡片從 registry 自動產生（名稱、說明、圖示在 `web/src/home/icons.tsx`）；舊版拆成好幾個工具時（例如 trpg-lab），
   全部上線後把它從 `web/src/home/entries.ts` 的 `LEGACY` 移除。README 與 ATTRIBUTION（靈感來源清單）更新；PLAN.md 進度表打勾。

## 6. 新工具引入流程（往後一律如此）

1. **評估**：功能、授權與條款、是否依賴作者的後端或外部服務、台灣玩家是否用得上。授權決定素材與文字能不能沿用（第 0 節）。
2. **規格**：實作者讀原作程式寫功能清單（第 1 節；放在 `docs/refactor/specs/`），對等驗證以此為準。
3. **差距分析**：列出需要的元件與模組，缺的先補進共用層。
4. **實作**：照第 3 節。
5. **對等驗證**：和原作並排比對（原作在本機跑起來比對；連不到時以規格的量測值為準）。
6. **上線**：首頁卡片、README、靈感來源清單。
